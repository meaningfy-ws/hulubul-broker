## 14. Known Issues / Follow-ups

- [x] 14.1 **Resolved.** LF-70 write-operation decision-level nondeterminism (createDeliveryRequest/updateDeliveryRequest/setRequestStatus): a well-formed, schema-valid `DataOperationResult(outcome="rejected", success=false)` was observed for scenarios that should have confirmed. Root-caused via live-traced reproduction: `write_neo4j_cypher` (the MCP tool) never returns a write query's own `RETURN` clause values -- regardless of what the Cypher specifies, its response is always exactly `{"_contains_updates": bool, "properties_set": int}`. The system prompt wrongly assumed the tool would hand back `requestId`/`currentStatus`/`updated`/`affectedRequests` directly. Faced with a write that had actually succeeded but gave it no way to read the new state, the model made an unnecessary post-write "verification" read -- which naturally reflected its own just-completed write, no longer matching the pre-write `expected_updated_at` it still held, so it concluded (wrongly, confidently, in a fully valid contract shape) `CONCURRENT_MODIFICATION` against its own successful write. Fixed by rewriting the prompt to explain the tool's actual response shape and to split the post-write read into two explicit modes: a **fetch** (after a confirmed success, populate result fields, never compare against the stale pre-write timestamp) versus a **classification** read (only after a genuine zero-row match). Verified: create 4/4, update 5/5, status 7/7, read 5/5, all previously-flaky scenarios now passing repeatably. Full details: `DEV/knowledge/checkpoint8-lf70-troubleshooting-runbook.md`, bug #20.
- [ ] 14.2 **Open.** `infra/docker-compose.yaml`'s `neo4j-schema` service (started by `acceptance-up`, gated on by `mcp-neo4j`/others via `service_completed_successfully`) is a no-op stub -- it only runs `echo "Waiting for Neo4j schema setup signal..." && exit 0` and never calls `infra/scripts/neo4j-setup-schema.sh`. `operationalconversationbinding_sessionid_unique` and every other constraint/index in `infra/cypher/schema.cypher`/`operational-schema.cypher` is therefore absent on any fresh stack unless `make neo4j-schema` is run against it by hand afterward. All of checkpoint 8's LF-70 verification (21/21 integration tests, including `test_atomicity_rollback_on_binding_conflict`) ran only against this machine's persistent dev Neo4j, where the constraint was applied manually mid-session -- never against a stack brought up fresh via `acceptance-up`. Not currently causing failures only because `ci-acceptance`/`ci` isn't wired into `.github/workflows/ci.yaml` yet (it runs only `ci-static`). Must be fixed as part of 13.2 (the CI stage that "start[s] the clean stack, appl[ies] schemas, deploy[s] exactly three flows...") before that stage goes live -- either make the `neo4j-schema` service actually run the setup script, or have the new CI stage call `make neo4j-schema` explicitly after `acceptance-up`. Full details: `plan.md`'s "Known Issues / Follow-ups" section.
